## 1. Abstract

The Smart Home Management System is a Java desktop application for recording and managing rooms and household devices through a Swing user interface backed by MySQL. It provides account registration and sign-in, role-controlled administration, device and room maintenance, ON/OFF controls, estimated energy reporting, recurring device schedules, activity history, periodic dashboard refresh, optional simulated sensor readings, and typed rule-based automation. Java Database Connectivity (JDBC) connects the application to MySQL, while Maven manages compilation and dependencies.

The system estimates energy from device rated power and the duration for which the application has recorded a device as ON. This estimate is not a meter measurement. Temperature, humidity, and motion readings can be generated by an explicitly labelled simulator; they are not physical sensor observations. Schedules and automation rules run in the desktop application process and cannot execute while that process is closed. Automated tests cover selected service logic, DAO transaction behavior using a JDBC test double, recurrence calculations, and presentation preferences. No claim of live-database integration testing or measured performance is made in this report.

## 2. Introduction

Connected-home devices need an interface through which occupants can organize equipment, view its recorded state, and coordinate routine actions. This project implements such a management interface as a desktop application rather than as a web application or embedded-device controller. Swing presents the screens; DAO classes isolate database access; service classes hold authorization and selected business rules; and the relational schema stores device, room, account, schedule, usage-session, and activity data.

The application is designed for a locally configured MySQL service. Device status is the state stored in the database. It should not be interpreted as proof that a physical appliance received or completed a command. The dashboard periodically requests fresh database state without blocking Swing's event dispatch thread. Optional automation rules evaluate stored sensor samples or a scheduled local time and can update a device's stored ON/OFF state.

## 3. Problem statement

Managing household device records, their room assignments, their stored ON/OFF states, and routine state changes without a unified application can require separate lists and manual database operations. The project addresses the need for a single desktop interface that persists these records, limits administrative operations by user role, provides a history of application-recorded actions, and presents a transparent estimate of energy usage based on available runtime history.

The system does not solve physical-device communication, physical sensor integration, utility-grade energy measurement, or always-on scheduling. These are outside the implemented scope.

## 4. Objectives

1. Provide a Java Swing application to manage a MySQL-backed home inventory.
2. Organize devices by rooms and support validated device and room maintenance.
3. Allow authorized residents to view and control recorded device status.
4. Restrict administration functions through backend service authorization.
5. Estimate energy from rated watts and tracked ON intervals, and expose the assumptions.

### 6.2 Limitations

- **No physical IoT control:** status changes and schedules update application/database state; they do not send commands to smart plugs, relays, or appliances.
- **Estimated rather than measured energy:** energy uses configured rated watts multiplied by tracked ON duration. The application has no meter or smart-plug measurement ingestion.
- **Partial history:** runtime before the energy tracking start time is unknown. Changes performed outside the application or by older builds are not guaranteed to be recorded.
- **Desktop scheduler availability:** enabled schedules execute only while the desktop application and scheduler are running. It is not an independent always-on service.
- **Monitoring/automation availability:** automation evaluates only while this desktop app is running. The sensor simulator is optional and disabled by default; no physical sensor interface is implemented.
- **Simulated readings:** generated temperature, humidity, and motion values are plausible demo data, not observed environmental conditions. There is no calibration or physical sensor acquisition.
- **Rule evaluation logging:** the system persists condition transitions, scheduled occurrences, suppressed attempts, and outcomes, not every background polling pass.
- **Sensor/history retention:** sensor and rule evaluation tables currently have no automatic retention or archive process.
- **Local database configuration:** the operator must provide MySQL credentials and create or migrate the schema.
- **No verified UI screenshot or performance benchmark:** none was supplied or measured during preparation of this report.
- **Device name uniqueness boundary:** the DAO checks duplicate device names before writes, but the existing `devices` table has no unique constraint for device name; external database writers can bypass this check.
- **Retention:** activity and execution history have no automatic archival/deletion process. README describes a manual archive recommendation, not an implemented retention job.
- **No live MySQL integration test result:** the listed automated tests do not establish that the student's specific MySQL server, credentials, certificates, or migrated data work.

## 8. System architecture

## 12. Database tables and relationships

The fresh-install schema defines twelve tables: `rooms`, `devices`, `energy_usage_sessions`, `device_status_history`, `energy_settings`, `app_users`, `device_schedules`, `schedule_execution_log`, `activity_logs`, `sensor_readings`, `automation_rules`, and `automation_rule_evaluations`.

- One room can contain many devices; each device has a required room (`ON DELETE RESTRICT`).
- One device can have multiple closed energy sessions, with a uniqueness rule allowing at most one open session per device. The session table stores name/type/room/power snapshots for historical estimation.
- Device status history stores timestamped state snapshots.
- `energy_settings` stores the configured tariff and earliest history start.
- A user may create schedules. Schedules reference devices and are deleted when the referenced device is deleted; schedule history survives schedule deletion by setting its schedule reference to `NULL`.
- Activity rows may reference users, devices, and schedules. Deletion preserves the activity row by nulling those optional foreign keys; descriptive snapshots remain.
- A unique `(schedule_id, occurrence_at)` key helps prevent duplicate logging for one scheduled occurrence.
- `sensor_readings` stores room-linked temperature, humidity, or motion values, a `simulated` marker, and UTC timestamp. Room deletion cascades to its sensor history.
- `automation_rules` stores a constrained condition type, optional threshold/room/time, existing target device, ON/OFF action, timezone, cooldown and persisted trigger state. Device or sensor-room deletion removes the dependent rule.
- `automation_rule_evaluations` stores rule-name snapshots, condition/action outcome and UTC timestamp. Deleting a rule preserves history with a nullable rule reference.

The full database dictionary and schema are in [03-database-reference.md](03-database-reference.md).

## 13. Module descriptions

### 13.1 Authentication, roles, and profile

`AuthenticationDialog`, `AuthenticationService`, `UserDao`, `UserRepository`, and `PasswordHasher` implement login and registration. Passwords are hashed with Argon2id using Bouncy Castle, random salts, and encoded algorithm parameters. New public registrations receive `RESIDENT`; initial administrator creation is an explicit terminal command that requires a console and does not embed a default password. The user DAO checks uniqueness and the service authorizes protected operations. A `session_version` increment on password change invalidates older sessions at the next protected service call. ADMIN manages accounts; role checks are also applied in service methods.

### 13.2 Dashboard and navigation

`MainFrame` composes a sidebar, page header, status/footer area, and data panels. Dashboard summaries use actual database records. Sidebar pages include Dashboard, Devices, Rooms, Energy Usage, Schedules, Automation Rules, Activity Logs, User Management, and Settings; access is role-dependent. `DashboardFrame` remains as a deprecated compatibility subclass of `MainFrame`.

### 13.3 Device management

`DeviceTablePanel` and `DeviceDialog` provide list, search, room/type/status filters, add/edit/delete, per-device ON/OFF, and confirmed bulk status actions. `DeviceDao` uses JDBC prepared statements, validation and transactions for state changes and related records. Room options are loaded from MySQL. Database operations are performed in background workers by the UI flows.

### 13.4 Room management

`RoomsPanel`, `RoomDialog`, and `RoomDao` provide room cards and room-associated device views, floor and device summaries, add/edit, and deletion checks. A room containing devices cannot be deleted.

### 13.5 Energy usage

`EnergyPanel`, `EnergyUsageDao`, and `EnergyAnalytics` show current ON rated power by room and type and aggregate runtime-based estimated kWh into daily, weekly, or monthly buckets. The user may configure a tariff, apply date/room filters, and export reports to CSV. The current estimate is not measured consumption.

### 13.6 Schedules

`SchedulePanel`, `ScheduleDialog`, `ScheduleDao`, `ScheduleRecurrence`, and `ScheduleService` implement persisted one-time, daily, and selected-weekday schedules. Timezone IDs are stored. Java timezone rules resolve daylight-saving gaps and overlaps; repository documentation says gap times move forward and overlap times use the earlier offset. The service runs in the desktop process and is shut down when the window closes.

### 13.7 Activity logs and notifications

`ActivityLogDao` and `ActivityLogService` persist/query activity, including successful operations and supported failure events. The UI provides filters and bounded pages (50 rows in the screen path; DAO clamps page sizes to 100). The header notification area shows recent actions/errors from stored records; the dashboard's compact activity list is session-only. No automatic activity-log retention job is implemented.

### 13.8 Appearance and settings

`UiStyle` supplies shared Swing styling and theme preference support. The preference is stored with `java.util.prefs.Preferences` per account on the current machine, not in MySQL. Settings contains profile/password/theme/logout operations.

### 13.9 Live monitoring, simulated sensors, and automation

`MainFrame` uses a configurable Swing `Timer` for dashboard refresh scheduling. An `AtomicBoolean` allows at most one database refresh worker at a time; JDBC reads run in `SwingWorker`. Successful refreshes display a last-refreshed timestamp and current database device states. Database or V7 migration failures are shown in the dashboard and status area rather than silently replacing state.

The dashboard provides a per-account refresh interval (5–60 seconds), simulator enable/disable control, and sample interval. `SensorSimulator` creates bounded random-walk temperature and humidity values and sparse motion events for each room, then writes timestamped, `simulated=TRUE` rows in a transaction. Simulation defaults to disabled; the dashboard clearly marks generated values. No physical sensors are polled.

`AutomationPanel` and `AutomationDialog` manage ADMIN-only rules. `AutomationRuleService` revalidates the active authenticated session and ADMIN role for every management operation. `AutomationDao` uses prepared statements, verifies a target device exists and meets condition-specific target type requirements, and updates target state through the existing transactional `DeviceDao` method. Conditions are fixed enum values; the user cannot enter SQL or commands.

`AutomationEngine` evaluates enabled rules on one background executor every five seconds. Temperature/humidity comparisons are strict `>` comparisons. Sensor rules trigger on a false-to-true edge; persisted condition state prevents repeated actions while a sensor value remains true. A cooldown suppresses a transition that occurs during the cooldown window; it is not retried until the condition becomes false and then true again. Motion rules require a Light-type target and ON action; temperature rules require a target type containing “climate” or “cool”. Sensor samples older than 120 seconds are treated as unavailable, and simulated samples are ignored when simulation is disabled. Scheduled-time rules use the local timezone stored on the rule and trigger at most once per local date; a nonexistent local time during a daylight-saving gap resolves forward under Java's timezone rules. Evaluation history records condition transitions, scheduled occurrences, suppressed attempts, and outcomes rather than every polling pass. Services are stopped when the window closes or the user logs out.

## 14. Algorithms and workflows

### 14.1 Sign-in and authorization

1. Validate that username and password are non-empty.
2. Retrieve account credentials by username.
3. Verify account enabled state and compare submitted password against stored Argon2id parameters/hash.
4. Return an authenticated principal or a generic incorrect-credentials message.
5. Before protected service operations, verify account existence, enabled state, role, and matching session version.
6. Require ADMIN for administration methods; RESIDENT actions are limited to permitted reads and device controls.

### 14.2 Live dashboard refresh

1. A Swing `Timer` fires on the event dispatch thread at the stored interval (5, 10, 15, 30, or 60 seconds) only when the Dashboard page is active.
2. The refresh guard rejects a new worker while a refresh is still in progress.
3. `SwingWorker.doInBackground` reads rooms, devices and the latest sensor reading per room/type from MySQL.
4. The `done` handler updates summaries, states and the last-successful-refresh time, or displays a connection/migration error.
5. Closing or logging out stops the Swing timer and awaits shutdown of the sensor simulator, automation engine, and schedule service.

### 14.3 Device status update

1. Validate requested state (`ON` or `OFF`).
2. Begin a JDBC transaction and lock/read the device record.
3. If state changes from ON to OFF, close the open usage interval.
4. Update device status; record status history; if state becomes ON, open a usage interval.
5. Record the associated activity event.
6. Commit only when the whole operation succeeds; roll back on SQL or runtime failure.

### 14.4 Energy estimate

For each tracked ON interval, the service computes:

`estimated kWh = rated power (W) × ON duration (hours) ÷ 1000`

Intervals are clipped to the selected report range and history start, then grouped into the selected calendar buckets in the system timezone. Cost is:

`estimated cost = estimated kWh × configured tariff per kWh`

This calculation assumes constant rated power while the record is ON. There are no live watt readings or meter-supplied kWh values; the separate environmental sensor model does not measure electrical energy.

### 14.5 Schedule recurrence and execution

1. Validate device, action, local date/time, timezone, recurrence, and weekday selection.
2. Calculate next occurrence using the selected `ZoneId` and recurrence pattern; persist local schedule details and next-run time.
3. While the application runs, the schedule service looks for due work.
4. Execute each due occurrence through DAO transaction logic; update device, status/energy history, and execution/activity logs.
5. Use a unique schedule-occurrence key and database locking to guard duplicate processing.
6. On startup, resume enabled schedules. Overdue recurring occurrences move to a future occurrence; an overdue one-time occurrence is marked missed as described in README.

The scheduler only changes recorded database state; no physical device command is sent.

### 14.6 Rule evaluation and safe action

1. Load enabled rule identifiers from MySQL; each rule is evaluated in a transaction while holding a row lock.
2. Sensor rules obtain the latest room/type sample. A sample older than 120 seconds is considered stale and does not satisfy a condition.
3. Temperature and humidity rules compare reading to threshold using strict greater-than; motion is true when the latest numeric value is positive. Scheduled-time rules compare local time to the configured minute and check that the local date has not already run.
4. For sensor rules, compare current condition with persisted `last_condition_met`; only a false-to-true transition is actionable. A persisted `last_scheduled_date` prevents repeating a scheduled rule during the same date.
5. If cooldown is active, record a suppressed evaluation and do not change device state. Otherwise, update device status/history/session using the existing `DeviceDao` method on the same connection and transaction.
6. Persist rule state, evaluation result, and activity records. On action failure, roll back the attempted state change and record a failed evaluation in a follow-up transaction where the database is reachable.

### 14.7 Account bootstrap

Run `mvn exec:java "-Dexec.args=--create-admin"` from an interactive terminal after database configuration. The command reads password and confirmation without echo, requires 12 or more characters through service validation, rejects a second administrator bootstrap, and clears the in-memory character arrays after use.

## 15. Implementation details

### 15.1 Build and dependencies

[`pom.xml`](../pom.xml) sets `maven.compiler.release` to 26 and configures compiler, exec, Surefire, and JAR plugins. Runtime dependencies are MySQL Connector/J 9.3.0 and Bouncy Castle 1.80; JUnit Jupiter 5.12.2 is test-scoped. No Spring, JavaFX, browser UI, or external chart dependency is used.

### 15.2 Data access and safety

DAO classes use `PreparedStatement` for user values and try-with-resources for JDBC resources in reviewed paths. Multi-step device and schedule operations use explicit transactions. `Database` loads settings from environment variables before `.env`, refuses blank database credentials, and requires `sslMode=VERIFY_IDENTITY` for remote MySQL URLs. The local example disables TLS and is intended only for local/trusted connections.

### 15.3 Swing concurrency

The entry point initializes the login UI on the Swing event dispatch thread. Main-frame flows use `SwingWorker` to perform database work off the event thread and publish state/UI updates in completion handlers. This documentation does not claim every possible Swing listener has been exhaustively audited by a static analyzer.

### 15.4 Configuration

Create a project-root `.env` file (ignored by Git) with:

```dotenv
SMART_HOME_DB_URL=jdbc:mysql://localhost:3306/smart_home_db?sslMode=DISABLED&serverTimezone=UTC
SMART_HOME_DB_USER=your-database-user
SMART_HOME_DB_PASSWORD=your-local-password
```

For remote MySQL, configure an identity-verifying TLS URL with `sslMode=VERIFY_IDENTITY`, valid certificate trust and matching hostname. Do not place real credentials in source control or the academic report.

### 15.5 SQL setup

For a new database run [`database/smart_home.sql`](../database/smart_home.sql) once. For an existing database based on the original rooms/devices tables, run V2 through V7 once and in order. These migration scripts are not all idempotent; do not apply them over the fresh-install schema. See [03-database-reference.md](03-database-reference.md).

The fresh-install script inserts four example rooms and three example devices if their names are not already present, and starts an energy session for devices seeded as ON. These are schema-provided starter records, not observations of a user's home or measured test results.

## 17. Installation and execution in VS Code on JDK 26

1. Install JDK 26, Maven 3.8+, MySQL 8+, and VS Code with the Extension Pack for Java.
2. Open the repository root (`SmartHome`) in VS Code and allow Java/Maven project import to finish.
3. Confirm the integrated terminal uses JDK 26:
   ```powershell
   java -version
   mvn -version
   ```
4. Start MySQL. In MySQL Workbench, open and execute `database/smart_home.sql` for a fresh install. For an existing database, back it up and execute migration files V2, V3, V4, V5, V6 in order; do not execute both setup paths.
5. Create the repository-root `.env` using the local template in Section 15.4. Use environment variables instead if preferred. Do not commit the file or share its password.
6. Verify Maven compilation/tests:
   ```powershell
   mvn clean verify
   ```
7. From a terminal with console input, create the first administrator:
   ```powershell
   mvn exec:java "-Dexec.args=--create-admin"
   ```
8. Launch the application:
   ```powershell
   mvn exec:java
   ```
9. Alternatively, use VS Code Java Projects/Run on `src/main/java/com/smarthome/Main.java` or run the `com.smarthome.Main` main class. The first-admin command must run in a terminal that provides `System.console()`.

The exec plugin in [`pom.xml`](../pom.xml) defines `com.smarthome.Main`, so `mvn exec:java` is sufficient. The project does not currently configure a shaded/uber JAR with bundled dependencies; `mvn package` creates the Maven artifact but `java -jar` should not be advertised as a standalone launch unless packaging is changed.
